**Session summary (2026-10-01 — injuries-refresh statement timeout logged as
an aborted transaction):**

Hourly runs 40ab88f5 (20:17 UTC) and a4a04838 (20:58 UTC) wrote
`pipeline_log` step `injury` status `error` (log_id 115154 at 20:21:07Z,
duration 165.6s; log_id 115196 at 21:02:06Z, duration 189.5s). Both

until end of transaction block`. The last successful injury rows that day

- **What was measured.** `injuries` is 818,566 live rows, 120 MB heap, and
  the only indexes were `(sport, team, report_date)`, `(player_name, sport)`
  and the primary key. `EXPLAIN` of the athlete-name `DISTINCT ON (player_id)
  … ORDER BY player_id, created_at DESC` is a seq scan plus a sort of 822,508
  rows, cost 145558. `EXPLAIN SELECT MAX(created_at) FROM injuries` is a
  parallel seq scan, cost 22406. `EXPLAIN SELECT created_at FROM injuries
  ORDER BY injury_id DESC LIMIT 1` is an index scan backward, cost 0.42..0.46.
  No open PR addressed this; #857 is the view-migration lock fix and was
  left alone.
- **What changed.** A timeout on the shared connection (return ramp) or on
  the name-seed connection now `ROLLBACK`s before the next command and
  before `close()`. `pipeline_log` records the first error (`QueryCanceled:
  canceling statement due to statement timeout`), not the follow-on.
  Successful sports commit before a later failure can roll them back.
  Freshness reads the newest `injury_id` instead of `MAX(created_at)`.
  Names are one row per athlete in `injury_player_names`, filled once by
  migration `injury_player_names_2026_10_01.sql` (partial index
  `idx_injuries_player_id_created`, then the backfill) and maintained on
  insert. A missing names table does not fail the injury insert and does
  not fall back to the full-log sort. No pause, no threshold, no
  calibration change, no production write from this session.
- **Verified.** `tests/test_injury_refresh_rollback.py`,
  `tests/test_injury_fetch_speed.py`, `tests/test_injury_player_names_migration.py`,
  plus `test_intraday_freshness`, `test_db_schema_split`, `test_db_setup`,
  `test_refresh_pass_parallel`, `test_nfl_injury_ingest`,
  `test_injuries_status_ts_migration`: 70 passed.
  `EXPLAIN` was not `EXPLAIN ANALYZE`; the ~63s and ~22s figures are the
  ones reported from auto-explain, not re-timed here.

**Session summary (2026-10-01 — NHL early weeks backtested: no hold was needed,
and the blended inputs built to replace the live ones graded worse — nothing
switched):**

mike, on a proposed 10-game hold: *"no, this is fucking why we have back

backtest, and the alternative input design, built and tested.

- **Result.** `scripts/nhl_early_season_blend.py`, walk-forward, fixed
  parameters, test seasons 2021-22 -> 2025-26. The live inputs return -0.6% /
  +0.1% / -4.9% at DraftKings in the early window (a team under 10 games)
  against -3.0% / -3.8% / -3.7% over the rest of the season. The hold was not
  supported by the data; the proposal was wrong.
- **The alternative.** `data.nhl_asof.TeamBook.inputs`: goals for and against,
  home / road scoring and a points rate, each blended toward the team's last
  season by games played, a row for every game including a team's first. New
  feature list `NHL_H2H_FEATURES_BLENDED`. It keeps the 333 games 2018-19 ->
  2025-26 the live list drops from training. It is not better: same-game log
  loss 0.6875 against 0.6843, units worse in both windows at every cut. On the
  225 games it was built for, the live list scored the way production scores
  them (last season's final row standing in) is the more accurate: 0.6650
  against 0.6786, DraftKings 0.6500.
- **Retrained anyway, to grade the real thing.** Both models, `--no-register`,
  100 Optuna trials each, graded with `scripts/nhl_live_artifact_grade.py
  --artifact` (new option). Moneyline 2025-26 raw edge >= 0.04: -13.0% on 308
  bets (-25.4..-0.6) against the live artifact's -0.3% on 341. Regulation as it
  runs: 320 bets, -55.8 units, against 300 bets, -39.2. **Not registered.** The
  candidates are not in the repo.
- **What ships.** `FEATURE_MAP` and the scorer are untouched; the blended
  columns are computed on the training path only, so production reads and does
  exactly what it did. `build_training_dataset(feature_cols=...)` so an
  artifact can be graded on the frame its own list builds. No `Updated-By`:
  nothing a model does has changed.
- **A design that was tried and removed before commit.** The blended columns
  were first wired into the scoring path too (one cached read of the team log
  per pass) with a scorer guard. With the design not adopted that was a read
  and a branch for columns no live artifact lists, so both came out.
- **Verified.** Eight new cases in `tests/test_nhl_asof.py`; the blend cases
  watched failing with the blend removed. A first version of the scorer-guard
  test passed with the guard deleted (the scorer swallows a prediction error
  into the same empty list) and was rewritten before the guard was dropped.
  Full suite: the failing set is identical to master's.
- **Fixed on the way: an unbounded read in the NHL training path.** It read
  every NHL DraftKings odds row ever stored, sorted in the database, and the
  live season is polled every few minutes. During this session it was cancelled
  by the statement timeout twice in a row, which fails `models.trainer` and
  every NHL backtest. The database was busy then (a by-game read timed out a
  few minutes later as well), so the growth of the table is not proven to be
  the whole cause; the read is now by game id for the seasons asked for
  (`_build_bulk_nhl_lookups`) either way, and the grading script reproduces the
  same numbers through it. That script's sums are now order-independent (two
  cells moved by 0.1 unit between runs before).
- **Found on the way.** The live home / road scoring split spans two seasons
  until New Year and one after; training uses this season only. Follow-up.
