**Session summary (2026-09-03, session 171 — the worker image was 60% GPU driver and dashboard it never runs):**

- Continuation of 169. A deploy on 2026-09-02 STALLED pushing the worker image:
  618 MB in, the push fell to ~65 KB/s and the container did not go live for
  over half an hour while `pollers` finished the same commit in 2.5 minutes. A
  1.17 GB image is not merely slow, it is a failure mode.

- **Measured from the installed tree, not guessed:**

  | package | installed | why it was there |
  |---|---|---|
  | `nvidia-nccl-cu12` | **475.7 MB** | transitive dep of `xgboost` on Linux |
  | `xgboost` | 239.0 MB | 19.3 MB as `xgboost-cpu` |
  | `plotly` | 58.9 MB | imported ONLY by `dashboard/app.py` |
  | `pydeck` | 47.5 MB | nothing imports it directly |
  | `matplotlib` | 37.0 MB | nothing imports it directly |
  | `streamlit` | 33.0 MB | imported ONLY by `dashboard/app.py` |

- **`xgboost` -> `xgboost-cpu`. Same project, same version, same import name,
  no CUDA kernels.** The repo asks for a GPU in exactly zero places (no
  `gpu_hist`, no `device='cuda'`, no `gpu_predictor`), so 475.7 MB of NCCL was
  riding along for a device that does not exist on the container. **Verified
  rather than assumed: all 37 committed xgboost artifacts predict
  BYTE-IDENTICALLY under xgboost-cpu** — same SHA over a fixed random matrix.
  Together with xgboost's own 239 -> 19.3 MB that is **~695 MB gone**.

- **streamlit + plotly moved to `requirements-dashboard.txt`.** They are the
  only packages in the repo that nothing outside `dashboard/` imports, and the
  dashboard runs on Matt's machine, never on the worker whose start command is
  `python scheduler.py`. Install is additive: `pip install -r requirements.txt
  -r requirements-dashboard.txt`. The three places that tell a human how to
  start the dashboard (CLAUDE.md §5, `docs/local_ops.md`, and
  `run_pipeline.py`'s own closing log line) all now name the install, because a
  split nobody can discover is just a broken command.

- **`tests/test_worker_deps.py` is the tripwire**, and it reads the requirements
  files as TEXT on purpose: what matters is what gets INSTALLED on the
  container, which is not observable from whatever environment a test happens
  to run in. It also pins the PREDICATE behind the split — the moment a module
  outside `dashboard/` imports streamlit or plotly, or anything asks for GPU
  training, the test fails rather than letting the container ImportError at boot.

- **Watched fail:** plain xgboost restored fails 1; streamlit back in the worker
  file fails 1; a non-dashboard module importing plotly fails 1; a module asking
  for `gpu_hist` fails 1; the dashboard file no longer saying it is additive
  fails 1. Suite **2,141 passed**.

- **THE `odds` COVERING INDEX WAS CONSIDERED AND DECLINED, and the reversal is
  the point.** Session 169 recommended it as the belt-and-braces follow-up while
  the query ran ~120x/hour. Re-measured once #398 was live: the DK pre-game
  subset is **744,586 rows** (35% of the table), `odds` already carries **443 MB
  of indexes** on a **5,725 MB** database, and a covering partial index with
  seven INCLUDE columns lands at roughly 100-150 MB PLUS a permanent write tax
  on the hottest table in the system — one the live loops write to constantly.
  The benefit it now buys is ~45 minutes a day of read time on a query that
  runs **5.5x/hour**. At 120x/hour that trade was clearly worth it; at 5.5 it is
  not. **Recorded so nobody re-derives it: if the poll interval drops, the
  re-seed interval shortens, or another caller starts hitting
  `last_known_prices`, re-run the arithmetic before assuming the answer is still
  no.**

- **Also verified this session:** #398's fix, in production. 23:18Z 4,291 calls
  / 88,398 s; 04:43Z 4,321 / 89,055 s — **+30 calls over 5.42 h = 5.5/hour
  against ~120/hour before, a 95% cut**, and 121 s/hour of database time against
  ~2,472. The mean is unchanged at 20,610 ms, which is the point: the query was
  not made faster, it was made rare.

**Session summary (2026-09-03, session 174 — retention keeps the CLOSE, and the first version of it timed the pruner out):**

- mike: *"keep one non-dk snapshot per day."* Option 2 from `docs/best_line.md`
  §4, chosen over raising `PRUNE_NON_DK_KEEP_DAYS` wholesale (~19 GB).
- **What was actually missing was the CLOSE, not the count.** After `keep_days`
  the pruner already kept exactly one non-DK row per (proposition, book) — but
  it was the **OPENER**, and an opener cannot answer either question the
  retained history exists for: the best price available at DECISION time
  (Stage 2's re-sweep, for propositions that never got a scored row) or "did the
  best book beat DK at close?" — the feature this module's own docstring warned
  would need closing snapshots retained BEFORE anyone relied on it. So the
  change keeps opener AND close, which is two rows, not one.
- **Cost, measured not estimated:** one day of non-DK rows is 297,975 in `odds`
  and 105,105 in `player_prop_odds`, thinning to 2,787 and 6,594 distinct
  (proposition, book). The second retained row is about **+6 MB/day** against
  the ~210 MB/day full retention would cost.
- **The first version of this change broke the job, and only running it caught
  it.** A second anti-join beside the opener's made `--dry-run` fail with
  `canceling statement due to statement timeout`, on a job that finishes in ~80s
  unchanged — verified by checking out `origin/master`'s copy and timing both.
  Two anti-joins over 2.2M and 2.5M rows is not the same shape as one. **A
  pruner that times out prunes nothing, and the growth it exists to bound is
  silent** — this would have been invisible until the database was much larger.
  Fixed by computing both keep-rules with two window functions over a SINGLE
  scan; `test_each_tier_uses_exactly_one_anti_join` is the tripwire.
- **The close must never be an in-play price** (§6: an in-play row is a
  different proposition). The DESC ranking is partitioned BY the pre-game flag,
  so `rn_last = 1 AND is_pre` is the newest PRE-GAME row rather than the newest
  row that happens to be pre-game. Verified against real rows for 2026-09-01:
  540 non-DK rows over 270 propositions, 332 kept — between 1× and 2× the
  proposition count, as it should be.
- Stated honestly in the module: it is the last pre-game-TYPED row, which is not
  automatically the last row before first pitch (§7's leak trap — the evening
  refresh keeps writing `open` rows after the game starts). `snapshot_at` is
  retained with it so an analysis can still apply the `<= commence_time` bound;
  what this guarantees is that a row EXISTS to be bounded, where before there
  was none.
- `tests/test_prune_preserves_openers.py` was updated for the rename
  (`select_openers` → `select_keepers`); the opener rule itself is unchanged and
  still asserted.
- **Also this session:** the sweep was re-run at mike's request and is
  byte-identical — same five-day window, no settlements between runs. Nothing to
  report is the report.

  `fix/pregame-best-line`. Design: **`docs/best_line.md`** (linked from §9).
  Ingest + display plumbing, so no `Updated-By` trailer.
- **The answer is three separate things and only two are bugs**, which is why
  the doc leads with the split rather than a fix list.
- **Bug 1 — two markets were fetched DK-only at the source.**
  `odds_ingestor._get_event_odds` hard-coded `bookmakers=ODDS_API_BOOKMAKER`,
  and it is the ONLY route by which MLB first-five and UFC round totals are
  fetched (both are "additional markets" absent from the bulk endpoint).

  the first draft of the doc said "zero extra credits", reasoning from the
  one-region rule. An A/B against the live endpoint on the same event says
  otherwise: F5 DK-only bills 1 credit and returns one market; F5 with all seven
  books bills **3** and returns three, because the endpoint bills per market
  RETURNED and only the other books offer F5 spreads and totals. UFC round
  totals is one market either way and does not move. Net ~+30 credits/day
  against 4,900,852 remaining — and it buys F5 spreads and totals, which this
  repo has never held. §1b exists for exactly this: the rule was right and the
  conclusion drawn from it was not.
- **Bug 2 — `_best_game_price` never tried the UFC sibling orientation**, which
  `_get_dk_odds` has done since the 2026-08-29 card. A fight five books had
  priced could silently stamp NULL, and it was invisible because "no quotes" and

  settlement and CLV measure against DK because every threshold was swept there.
  Moving that is Stage 2 and it is mike's call, not a defect to fix in passing.
- **The coverage numbers that opened the investigation were wrong, and I caught
  it mid-flight.** "MLB 48%, WNBA 12%, UFC 0%" pooled six pre-feature weeks with
  four post-feature days — best-line stamping only shipped ~08-28. On the clean
  window (since 08-31) it is **69 of 70** pre-game BETs, and the single miss is
  the UFC DK-only market from Bug 1. WNBA was never broken; its season ended
  08-30. This is §1b's "name the query AND what it excludes" in both directions.
- **The finding that mattered most, and it was not what was asked:**
  `BEST_LINE_BOOKMAKERS` defaulted to `LINE_SHOP_BOOKMAKERS`, which includes
  **pinnacle and bovada** — neither bettable from the US. Of the 69 clean-window

  removes a book from SHOPPING while leaving it in the feed — Pinnacle is the

  exclusion is a shared config constant, so live stamping stops naming

  call**, on the assumption that `IF NOT EXISTS` makes it free. Postgres
  disagrees on three counts: `CREATE INDEX IF NOT EXISTS` takes a SHARE lock
  before it discovers the index exists, `ALTER TABLE ... ENABLE ROW LEVEL
  SECURITY` takes ACCESS EXCLUSIVE whether or not RLS is on, and **each one
  fires Supabase's `pgrst_ddl_watch` event trigger — PostgREST then returns 503
  to the entire app until its schema cache rebuilds.** From
  `pg_stat_statements` (measured, not estimated):

  | statement | calls | mean | total |
  |---|---|---|---|
  | `CREATE INDEX IF NOT EXISTS idx_api_call_ts` | 1,925 | 15,082 ms | 29,032 s |

  ~3,600 forced cache reloads. `postgres_logs` shows the reload query itself —
