  **The control that makes it proof rather than a quiet window:** over the same

  and calling `ensure_schema` on every one of those; the DDL simply stopped
  firing. `mean_exec_time` also held to the digit, which one new execution
  would have moved.

- **A hypothesis raised and then killed by measurement.** Session 167 flagged
  that `job_queue` is the only guarded site passing an EMPTY `revoked_from`,
  and that an untyped empty array in `r.rolname = ANY(%s)` might raise, roll
  back, and fall through to `return False`. It does not — `worker_jobs` is
  frozen too. Recorded because the reasoning was sound and the conclusion was
  wrong; the measurement is what settled it.

- **THE TRIPWIRE SHIPPED IN 167 WOULD NOT HAVE CAUGHT THE NEXT ONE, AND ONLY A
  MUTATION SHOWED IT.** `tests/test_ddl_guard.py` grepped for `ENABLE ROW LEVEL

  Widening it to `CREATE INDEX` and `ADD COLUMN` did NOT fix that either: the

  to the symptom that had already been found, not to the mechanism.**

- **`CREATE TABLE IF NOT EXISTS` belongs in the tripwire, and execution time is

  which is why it looked skippable — but it fired 3,479 times from `job_queue`

**Session summary (2026-09-01, session 167 — the Stats page error was the whole API, and the cause was our own DDL):**

- Matt: *"Still having this error on the stats page and now no players are
  showing"* — two screenshots, NCAAF Pass Yards and MLB Hits, both showing
  `Connection error: [object Object]` above `No players`.

- **IT WAS NOT THE STATS PAGE, AND NOT THE DATA.** The RPCs behind the board are
  healthy: `player_recent_games_mlb(2026,'batter',5)` returns **3,197 rows in
  780 ms**, and it returns them as `anon`. `player_recent_games_ncaaf(2026,5)`
  returns 686. Grants are correct, the functions exist. The board was empty
  because **PostgREST was answering 503 to every request**. `edge_logs` for the
  minute in Matt's screenshot (10:11 UTC = 6:11 ET, the clock on the phone):
  **215 responses, all 503.** Every logged call to those two RPCs in 24h was a
  500 or a 503; not one succeeded.

- **THE CAUSE IS THIS REPO'S OWN write-time DDL.** Seven modules create their
  table at write time and re-ran the whole CREATE/ALTER/REVOKE block on **every
  call**, on the assumption that `IF NOT EXISTS` makes it free. Postgres
  disagrees on three counts: `CREATE INDEX IF NOT EXISTS` takes a SHARE lock
  before it discovers the index exists, `ALTER TABLE ... ENABLE ROW LEVEL
  SECURITY` takes ACCESS EXCLUSIVE whether or not RLS is on, and **each one
  fires Supabase's `pgrst_ddl_watch` event trigger — PostgREST then returns 503
  to the entire app until its schema cache rebuilds.** From
  `pg_stat_statements` (measured, not estimated):

  | statement | calls | mean | total |
  |---|---|---|---|
  | `CREATE INDEX IF NOT EXISTS idx_api_call_ts` | 1,925 | 15,082 ms | 29,032 s |
  | `ALTER TABLE api_call_log ENABLE ROW LEVEL SECURITY` | 1,676 | 7,797 ms | 13,067 s |

  **11.6 hours of database time re-creating a table that already existed**, and
  ~3,600 forced cache reloads. `postgres_logs` shows the reload query itself —
  PostgREST's giant catalog `WITH base_types AS ...` — timing out **232 times**
  against the 8s `authenticator` limit, plus 108 timeouts of the `ALTER TABLE`
  and 30 each on `v_latest_odds_all_books` / `v_latest_dk_odds` reads starved
  behind it.

- **It is self-reinforcing, which is why it got worse rather than settling.**
  `monitoring/probe.py`'s writer drops its connection on ANY failure and clears
  its `ensured` flag, so it re-runs the ensure block on reconnect. The busier
  the database got, the more DDL it fired at it, the longer the cache stayed
  down.

- **Fixed: `data/ddl_guard.py`.** One indexed catalog SELECT answers "would
  every statement in this block be a no-op?" — table exists, has the columns,
  has the indexes, RLS on, `anon`/`authenticated` hold nothing. It **fails
  open**: SQLite, a shim connection, an unreadable catalog, any doubt at all
  returns False and the caller runs its DDL exactly as before, so it can only
  remove redundant work. Uses `%s` placeholders and a cursor fallback so it
  works on both `data/db.py`'s shim and a raw psycopg2 connection.

- **Applied to all seven sites, not one** (§1b: a fix that lands in one module
  and not the others is how this repo accumulates work): `monitoring/store.py`,
  `tracking/run_ledger.py`, `tracking/live_calibration.py` (this one ran on
  every live-loop calibration pass), `models/probability_calibration.py`,
  `tracking/job_queue.py`, `data/ingestors/dk_direct_feed.py` (ACCESS EXCLUSIVE
  on `odds`, the busiest table in the database), and
  `nfl/live_model/backtest/backup_snaps.py` — the last one found by the
  tripwire, not by reading.

- **`tests/test_ddl_guard.py`** — 21 cases: the guard's own truth table, one
  no-DDL case and one still-creates case per site, and a source tripwire that
  fails if any NEW module runs `ENABLE ROW LEVEL SECURITY` without the guard.
  **Watched fail, not assumed** (§1b): removing the short-circuit from
  `monitoring/store.ensure_table` fails 1; making the guard always return True
  fails 13; making it stop failing open fails 1.

- **Fixed: `[object Object]`.** supabase-js does not throw — it returns
  `{ data, error }`, and every helper re-throws that plain object. `String(e)`
  on a plain object is literally `"[object Object]"`, and **16 call sites across
  the app** did exactly that. New `mobile/src/lib/errors.ts::errorText` reads
  `message` and `code` first (so `PGRST002` / `57014` reach the user), falls
  back to a sentence, and can never render `[object Object]`. All 16 sites plus
  `authHelpers` / `discordHelpers` / `billing` now route through it.
  `mobile/scripts/verify_error_text.ts` pins it — and fails 6 checks when the
  object branch is removed.

- **Fixed: the empty state lied.** `No MLB Hits data for the last 5 games yet.`
  is what a total API outage looked like — the same copy an genuinely empty
  board gets, which sent the diagnosis at the data rather than the API. The
  board now says "Couldn't load players" with a Retry in the banner when the
  fetch failed, and keeps the "no data yet" copy for an actually empty result.

- **Verified:** `python -m pytest -q tests/` → **1,961 passed**. `npx tsc
  --noEmit` in `mobile/` → error set **byte-identical to `origin/master`** (57
  lines, all the documented pre-existing `queries.ts` casts, 0 in touched
  files), diffed against a `git worktree --detach origin/master`, not a stash.
  `npx tsx scripts/verify_error_text.ts` → all pass.

- **Found and NOT fixed, deliberately:** `SELECT DISTINCT ON (o.game_id,
  o.market) ... FROM odds JOIN games` (`data/ingestors/pregame_line_poller.py`)
  was observed running **24–50 s on `IO / DataFileRead`** during the incident,
  and timed out 20 times in 24h. It is real, and it is the reason the DDL storm
  was able to starve everything else rather than just being wasteful — but it is
  a separate piece of work needing its own index measurement, and fixing it
  means a migration, which is itself more DDL. Flagged for the next session.

- **Not done:** the fix ships when the worker redeploys — the DDL flood
  continues from the running container until then. Nothing was changed in
  production from this session.
