**Session summary (2026-11-01 — app_timings CE Mediums from #1110):**

Follow-up to #1110 (merged as `6fe2db4a`, reviewed at tip `36a948fd`). Telemetry only: no model, threshold, stake, or pause change. No production write. The cap migration is hand-applied and was not run.

**M1.** `settle` in `mobile/src/lib/perfLog.ts` closed the launch window as screen `unknown` when auth/access/hydration finished and the network was quiet for 300 ms before navigation named the first screen. That launch row stopped at those early reads, and the real first screen opened a normal window. The launch window now stays open until it has a real screen name. Naming it restarts the join clock and, if the pre-nav reads have already finished, arms the quiet timer so the first screen's reads still join. `mobile/scripts/verify_perf_log.ts` covers that race. Watched failing first: the buffer held a launch row named `unknown` at 280 ms, and the later `Tabs` screen had no launch row.

**M2.** `data/app_timings_retention.py` deletes rows older than 45 days, in batches of 5,000. The daily pipeline runs it after the odds prune, and skips it on `--dry-run`. `python run_pipeline.py --step prune-app-timings` runs it alone. A missing table is a skip, not a red daily. `data/migrations/app_timings_cap_2026_11_01.sql` (not in `ACTIVE_MIGRATIONS`) adds nullable `user_id` and replaces `log_app_timings`: a signed-in caller is capped on `auth.uid()`, the count and the insert share an advisory lock, one call inserts at most the room left under 1,000, and `ms` / `status` / `request_count` / `since_launch_ms` are read as text and clamped. An anonymous caller is still capped only on the client device id. That rotation hole is unchanged; retention is what bounds the table. The 1,000 cap was not lowered, because a member who leaves the Live tab open is the population this table measures.

**Lows taken.** A batch the server rejects (HTTP 4xx or a 5-character SQLSTATE) is dropped instead of backing off forever; a network error still retries. The hourly overshoot and the uncapped integers are the cap migration above. Both hand migrations are named in `docs/app_timings.md`; neither was added to `ACTIVE_MIGRATIONS`, because the worker re-runs that list and this DDL reloads PostgREST's schema cache. `tests/test_app_timings.py` is on the pytest-subset list, which already installs Node 22, so the node checks run there. The skip for a machine without Node 22.6 stays.

**Not done.** `app_timings_cap_2026_11_01.sql` is not applied. Until it is, production still caps on device id only, and `user_id` does not exist. No App Store Connect change.
