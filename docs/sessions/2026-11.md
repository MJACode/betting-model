**Session summary (2026-11-01 — app_timings CE Mediums from #1110):**

**M1.** `settle` in `mobile/src/lib/perfLog.ts` closed the launch window as screen `unknown` when auth/access/hydration finished and the network was quiet for 300 ms before navigation named the first screen. **M2.** `data/app_timings_retention.py` deletes rows older than 45 days, in batches of 5,000. The daily pipeline runs it after the odds prune, and skips it on `--dry-run`. `python run_pipeline.py --step prune-app-timings` runs it alone. A missing table is a skip, not a red daily. `data/migrations/app_timings_cap_2026_11_01.sql` (not in `ACTIVE_MIGRATIONS`) adds nullable `user_id` and replaces `log_app_timings`: a signed-in caller is capped on `auth.uid()`, the count and the insert share an advisory lock, one call inserts at most the room left under 1,000, and `ms` / `status` / `request_count` / `since_launch_ms` are read as text and clamped. The 1,000 cap was not lowered, because a member who leaves the Live tab open is the population this table measures.

**Lows taken.** A batch the server rejects (HTTP 4xx or a 5-character SQLSTATE) is dropped instead of backing off forever; a network error still retries. The hourly overshoot and the uncapped integers are the cap migration above. Both hand migrations are named in `docs/app_timings.md`; neither was added to `ACTIVE_MIGRATIONS`, because the worker re-runs that list and this DDL reloads PostgREST's schema cache. `tests/test_app_timings.py` is on the pytest-subset list, which already installs Node 22, so the node checks run there.
