**Session summary (2026-11-02 — NCAAB first-half and team-total purchase at three game-day times; code only):**

mike approved the spend on 2026-11-02: a test buy of about 50 games at 15:00 UTC on game day, then, if books post first-half lines by then, the full 15:00 UTC buy for 2023-24 to 2025-26 (at most 687,686 credits); 18:00 UTC and 60 minutes before the tip follow on 2026-12-01. This change is the code only. It buys nothing; the purchases run later as worker jobs.

**What changed.** `data/ingestors/ncaab_odds_history.py --derivatives` takes three new times: `15z` (15:00 UTC on the game's ESPN date, only games that tip after it), `18z` (18:00 UTC, the same rule) and `tip60` (60 minutes before the tip, down to five minutes). Each stamps its own source (`odds_api_ncaab_derivative_15z`, `_18z`, `_tip60`), resumes on its own, and is protected from the odds clean-up. Markets, endpoint, credit meter, ceiling, floor, empty-answer handling and the per-date event list are the close and open purchase's own. `--sample N` buys N games chosen by season and Eastern tip time (15 groups, each ordered by a fixed hash of the game id, taking turns; only games with a stored close), then prints, per book and market, how many of the N hold a quote at the time beside how many hold one at the close, read back from `odds`. Without `--apply` a game-day run is a read-only dry run that builds no meter. Job modes in `tracking/job_queue.py`: `deriv_15z` (cap 700,000), `deriv_18z` (650,000), `deriv_tip60` (700,000), `deriv_15z_test` (2,500, 50 games); each takes `dry_run: true` with no limits. The close, open and opener grid code paths are unchanged.

**Verified.** `tests/test_ncaab_derivative_gameday.py` (61): each time for sample games, including tips at, before and without 15:00 UTC; the source each stamps; the sampler's spread and determinism; the report's table; the jobs' command lines and refusals; and that a dry run makes no HTTP call. **Calls side by side (same change, mike: "why taking so long ... I want it all done").** The opener grid and every first-half purchase send up to 6 paid calls at once (job arg `concurrency`, 1 to 10; `--concurrency`). Only the HTTP calls run in a thread pool (`PoolMeter.fetch`); writes, parsing, the keepers and the credit count stay on the main thread, and answers are handled in the order asked, so the stored rows match the one-at-a-time run (`tests/test_ncaab_paid_calls.py` compares both on a mocked feed: same rows, same order, same ledger). Before every call the meter counts each call in flight at its most (30 a snapshot, 40 a game), so calls in flight cannot cross the 300,000 floor or the job's limit; while the balance is unknown, one call at a time. A 429 pauses every call (2 s doubling to 30 s), is retried, and lowers the number in flight; the report counts them. A job whose stored args name no concurrency runs at 6, so the grid's job 936020, rerun after the redeploy, picks it up; its stored args validate. The grid's read-only dry run at 23:43Z counted 11,825 times already bought, between the ledgers' 11,821 and 11,826 rows over that read, so a rerun buys none of them again. Watched fail: with the calls in flight left out of the meter's check, four tests failed (the floor and the ceiling crossed).

**Session summary (2026-11-01 — app_timings CE Mediums from #1110):**

Follow-up to #1110 (merged as `6fe2db4a`, reviewed at tip `36a948fd`). Telemetry only: no model, threshold, stake, or pause change. No production write. The cap migration is hand-applied and was not run.

**M1.** `settle` in `mobile/src/lib/perfLog.ts` closed the launch window as screen `unknown` when auth/access/hydration finished and the network was quiet for 300 ms before navigation named the first screen. That launch row stopped at those early reads, and the real first screen opened a normal window. The launch window now stays open until it has a real screen name. Naming it restarts the join clock and, if the pre-nav reads have already finished, arms the quiet timer so the first screen's reads still join. `mobile/scripts/verify_perf_log.ts` covers that race. Watched failing first: the buffer held a launch row named `unknown` at 280 ms, and the later `Tabs` screen had no launch row.

**M2.** `data/app_timings_retention.py` deletes rows older than 45 days, in batches of 5,000. The daily pipeline runs it after the odds prune, and skips it on `--dry-run`. `python run_pipeline.py --step prune-app-timings` runs it alone. A missing table is a skip, not a red daily. `data/migrations/app_timings_cap_2026_11_01.sql` (not in `ACTIVE_MIGRATIONS`) adds nullable `user_id` and replaces `log_app_timings`: a signed-in caller is capped on `auth.uid()`, the count and the insert share an advisory lock, one call inserts at most the room left under 1,000, and `ms` / `status` / `request_count` / `since_launch_ms` are read as text and clamped. An anonymous caller is still capped only on the client device id. That rotation hole is unchanged; retention is what bounds the table. The 1,000 cap was not lowered, because a member who leaves the Live tab open is the population this table measures.

**Lows taken.** A batch the server rejects (HTTP 4xx or a 5-character SQLSTATE) is dropped instead of backing off forever; a network error still retries. The hourly overshoot and the uncapped integers are the cap migration above. Both hand migrations are named in `docs/app_timings.md`; neither was added to `ACTIVE_MIGRATIONS`, because the worker re-runs that list and this DDL reloads PostgREST's schema cache. `tests/test_app_timings.py` is on the pytest-subset list, which already installs Node 22, so the node checks run there. The skip for a machine without Node 22.6 stays.
